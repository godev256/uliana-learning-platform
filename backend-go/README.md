# ulianaa.math — Go backend

Часть общего Git-репозитория платформы. Go + PostgreSQL + Squirrel + JWT; Redis не используется. React/Vite frontend находится в корне проекта. Продакшен на Vercel эта разработка не меняет.

## Запуск на этом компьютере

Конфигурация `.env` уже создана с отдельными случайными ключами и не входит в Git. PostgreSQL и API могут быть уже запущены; `/readyz` проверяет подключение к базе.

Три терминала:

```sh
cd /Users/ulanaa/Desktop/website/backend-go
make db
```

```sh
cd /Users/ulanaa/Desktop/website/backend-go
make run
```

```sh
cd /Users/ulanaa/Desktop/website
./scripts/npm.sh run dev:go
```

- Frontend: http://127.0.0.1:5173/board
- Кабинет: http://127.0.0.1:5173/cabinet
- API: http://127.0.0.1:8081
- Проверки: `/healthz`, `/readyz`
- PostgreSQL: `127.0.0.1:55432`, база `ulianaa`; строка подключения в `.env`.

Существующие локальные аккаунты, их доски и файлы перенесены в PostgreSQL. Логины и пароли остаются прежними, но войти нужно заново: прежние непрозрачные сессии не импортируются. Доски, которые хранились исключительно в localStorage публичной `/board`, автоматически не переносятся; исходные локальные данные сохранены. В Go-режиме новые личные доски преподавателя и доски учеников сохраняются в PostgreSQL.

Остановка — Ctrl+C в соответствующем терминале. Файлы PostgreSQL остаются в `.local/pg-data`; последующий `make db` использует тот же кластер. Не удаляйте этот каталог. `cmd/devdb` нужен только для разработки без Docker; для сервера используйте Compose.

## Новый компьютер

Нужен Go версии из `go.mod` или новее, Node.js 24+ для существующего фронтенда. `scripts/go.sh` использует установленный Go; на текущем компьютере также поддерживается SDK из `../.local/toolchains/go`.

1. Скопируйте `.env.example` в `.env`.
2. Задайте отдельный пароль PostgreSQL в `DATABASE_URL` и случайный `JWT_SECRET` (например, `openssl rand -hex 32`).
3. Запустите `make db`, `make run`, затем `dev:go` из frontend.
4. На пустой базе локальный интерфейс предложит создать преподавателя. `ALLOW_LOCAL_SETUP` разрешён только с loopback-адресом API; на сервере он выключен.

Для явного создания преподавателя через CLI (ввод пароля скрыт):

```sh
set -a; . ./.env; set +a
./scripts/go.sh run ./cmd/admin create-teacher LOGIN
```

## Архитектура и хранение

Подробности: [ARCHITECTURE.md](ARCHITECTURE.md).

- `cmd/api`, `cmd/admin`, `cmd/import-local`, `cmd/devdb`: точки входа и сборка зависимостей.
- `internal/model`: модели и типизированные ошибки.
- `internal/repository`: интерфейсы; `postgres`: Squirrel с `$1…` и pgx через `database/sql`.
- `internal/service`: права доступа, валидация, операции с досками/PDF/профилями.
- `internal/handler`: HTTP, совместимый API существующего UI и REST-маршруты.
- `internal/auth`: JWT HS256 и совместимые scrypt-v2 хеши паролей.
- `migrations`: SQL, версии и контрольные суммы; применение атомарно под migration lock.

`boards` хранит метаданные и ревизию. `pages` содержит **каждый лист**, включая пустые. Объекты рисунка — JSONB; порядок объектов сохранён отдельно. Геометрия, дополнительные поля, 3D, выделитель и PDF-фоны сохраняются без переписывания данных рисунка. Сохранение всех листов и ревизии — одна транзакция. Устаревшая ревизия даёт 409, никаких частичных записей.

Вложения хранятся в PostgreSQL как неизменяемые части BYTEA. Ключ включает владельца; повторная передача тех же байтов допускается, подмена — нет. Профили, календарь и расписание также находятся в PostgreSQL. В базе нет пользовательских триггеров или хранимых процедур с бизнес-логикой. Идентификаторы, проверки и бизнес-операции выполняются в Go; ограничения и внешние ключи обеспечивают целостность данных.

JWT проверяется по алгоритму, issuer, audience и сроку. Браузер получает HttpOnly/SameSite cookie; API-клиент может использовать `Authorization: Bearer …`. Идентификатор JWT-сессии сохраняется в PostgreSQL для отзыва при выходе и смене пароля; секрет и сам токен в БД не сохраняются. Пароль с новым хешем и отзыв сессий меняются одной транзакцией. Redis и публичная регистрация преподавателей на сервере не требуются.

## API

Совместимость с текущим фронтендом: `GET/POST /api/account?action=…`:

`session`, `setup` (только локально), `login`, `logout`, `students`, `password`, `profile`, `topics`, `board`, `asset`.

REST:

| Метод | Путь | Действие |
|---|---|---|
| POST | `/api/v1/auth/login` | Логин/пароль, JWT и cookie |
| POST | `/api/v1/auth/logout` | Отзыв текущей сессии |
| GET | `/api/v1/auth/me` | Текущий пользователь |
| GET/POST | `/api/v1/students` | Список/создание ученика преподавателем |
| GET/POST | `/api/v1/students/{studentID}/boards` | Список/создание доски |
| GET/PUT | `/api/v1/students/{studentID}/boards/{boardID}` | Чтение/сохранение всех листов |
| PATCH | `/api/v1/students/{studentID}/boards/{boardID}` | Переименование преподавателем |

Для сохранения нужны `notebook: {items: […], pageCount: N}` и `revision`. Для записи через cookie требуется разрешённый `Origin` и `Content-Type: application/json`. Bearer-клиент без браузерного Origin также поддерживается. Ученику доступен только собственный ID; преподавателю — ученики и личное пространство.

## Проверки

При запущенном локальном PostgreSQL:

```sh
make test
make check
./scripts/go.sh build -o .local/bin/api ./cmd/api
PLAYWRIGHT_BROWSERS_PATH=../.local/playwright node scripts/verify-frontend.mjs
```

Go-интеграция использует отдельную случайную схему и удаляет только её после теста. Без `TEST_DATABASE_URL` PostgreSQL-тест явно пропускается; `make test` задаёт эту переменную из `.env`. Проверяются JWT, отзыв токенов, чужие кабинеты, профили, все листы/порядок объектов, потерянные ревизии, параллельные записи, неизменяемость файлов и отсутствие пользовательских триггеров.

Браузерный тест запускает отдельный Go API и Vite с тестовой схемой. Проверяет действующий React UI, личные доски преподавателя, два листа, права ученика, двустороннее вращение 3D, PDF и сохранность после перезапуска Go. Реальная локальная база не изменяется. Скриншоты — `.local/reports`.

## Перенос прежней SQLite

Экспортёр читает SQLite **read-only**; файл снимка создаётся с правами 0600 и не входит в Git. Импортёр работает в одной транзакции и отказывается писать в непустую базу.

```sh
node scripts/export-sqlite.mjs ../.local/accounts.sqlite .local/legacy-snapshot.json
set -a; . ./.env; set +a
./scripts/go.sh run ./cmd/import-local -file .local/legacy-snapshot.json
```

Импортируются аккаунты с существующими хешами паролей, доски/все листы/ревизии, профили, календарь и байты файлов. Сессии и счётчики прежних входов не переносятся. Сам snapshot содержит частные данные — храните его только локально.

## Сервер и GitHub

Production-конфигурация находится в `../deploy/`: Docker Compose, Caddy для двух доменов, ограниченный SSH-деплой, fail2ban и резервные копии. Workflow `../.github/workflows/deploy.yml` проверяет код, публикует образы Go API и frontend/Caddy в GHCR и раскатывает их на сервер. Подробности — [deployment README](../deploy/README.md).

Старые файлы `deploy/` внутри backend сохранены как локальный пример сборки. Для production используйте конфигурацию из корня проекта.

Согласованный экспорт текущей PostgreSQL без изменения исходной базы:

```sh
node --env-file=.env scripts/export-postgres.mjs .local/postgres-snapshot.json
```

Полученный snapshot приватный и не коммитится. Импортёр отказывается писать в непустую базу.
